\begin{abstract}
Deployed systems are not well equipped to deal with the dynamic security conditions at runtime for static security configuration. We introduce a multi-client end-to-end encrypted chat system using C11 on POSIX which makes security posture a runtime variable and not a compile-time constant. TLS~1.3 transport security is layered on top of Signal-protocol Double Ratchet at the application layer, and all messages are sent at once via both TCP and UDP. The three-state adaptive engine polls smoothed packet-loss rates, authentication errors per session, and replay-detected events once per second and immediately sends reconfigured cryptographic and transport parameters to all active sessions. All the message payloads are padded to the same length (4,096~bytes) and a new X25519 keypair is created per message in High-Risk mode, to resist traffic analysis and reduce the amount of exposure following post-compromise. A statically allocated intrusion-detection subsystem is based on a lightweight, real-time, per-IP authentication failures and replay events that are directly coupled to the engine's state machine, allowing threat detection and cryptographic responses to be performed within a single feedback loop. Deduplication is done on both delivery paths using a 128-bit message-ID ring buffer, and on-disk offline queue – messages to disconnected recipients are stored in the offline queue within an OS enforced access-control boundary. 13 functional tests are passed: Authentications are simulated by brute force, injected packet loss is simulated, and all tests are passed.
\end{abstract}

\section{Introduction}

In the last ten years, secure messaging has gone from a niche to a standard requirement in both civilian and operational settings. These systems have developed very good cryptographic primitives: TLS version 1.3 \cite{b3} offers session-level encryption that is authenticated and forward-secret at the transport layer; the Signal Double Ratchet algorithm \cite{b1} extends comparable guarantees to the individual message level. Much less discussed is the connection between an environment in which a system operates and the security stance of that system.

The majority of deployed secure messaging systems can be statically configured at design time and remain fixed over time as network conditions or hostile factors change. In practice, this is a significant restriction. When the link drops 20% of packets, it requires different behaviour to be applied to it when it is retried than when it is healthy; when a session is being brute-forced using active authentication, more frequent key rotations and IP-level blocking are warranted than for a quiet session. Such a distinction can only be made in a dynamic situation: either a posture is permanently configured for the worst case, thus wasting resources unless conditions are severe or a posture is optimized for the common case, leaving the system underdefended when conditions get worse.

A multi-client end-to-end encrypted chat system is described which implements security as a run-time parameter, realised in C11 on POSIX. It includes an adaptive engine that listens to network quality metrics and to IDS-identified security events to adjust encryption and transport parameters as needed, a three-state engine, a Signal-protocol Double Ratchet at the application layer, and TLS~ 1.3 transport security, as well as simultaneous dual-path message delivery over both TCP and UDP. A co-resident per-IP intrusion-detection subsystem (IDS) directly passes authentication failures and replay events to the engine's state machine. The main contributions of this work are:

\begin{enumerate}
    \item Three-state adaptive engine based on smoothed packet-loss rate, per-session authentication failure counter and a cumulative replay counter.
    \item Double Ratchet at the application level which includes per-message forward secrecy, and the ability to recover quickly if session-keys are compromised.
    \item Resilient delivery of messages over simultaneous dual-path delivery (TCP \& UDP) with 128-bit message-ID deduplication.
    \item Lightweight, statically allocated IDS that takes per-IP security events directly into the adaptive state machine, combining threat detection and cryptographic response in one feedback loop.
\end{enumerate}

A persistent offline message queue with timestamp ordered filenames allows ordered replay on a client reconnection without tying queue state to an active ratchet state, thus allowing for fully asynchronous delivery.

The rest of this paper is structured as follows. The related research is surveyed in Section~II. The overall system architecture is described in Section~III. The wire protocol is described in detail in section~IV, and the design of the cryptographic system is described in section~V. Sections~VI and~VII describe the adaptive engine and IDS integration and multipath transport and offline queuing. The results of evaluations are reported in Section~VIII. Section~IX discusses limitations and future directions, and Section~X concludes.

\section{Related Work}

\subsection{End-to-End Messaging Protocols}

A variant of the Double Ratchet Algorithm has emerged as the common structure of an asynchronous end-to-end encrypted messaging system: the Signal \cite{b1} protocol. The Double Ratchet is a variant of the ratchet that takes two interlocked key-derivation functions: a symmetric ratchet to generate a new key on every message sent, and a Diffie--Hellman ratchet to periodically add new entropy from a new ephemeral key exchange. The result is that if an attacker is able to recover the chain state at any point in time, they can't produce any keys for messages outside the current DH epoch. The first formal security proof for this construction was given by Cohn-Gordon et al. \cite{b2} who proved forward secrecy and post-compromise security. Our implementation is a straight copy of the Double Ratchet specification, with DH ratchet frequency being adaptive, increasing automatically when the conditions are bad.

\subsection{Transport Layer Security 1.3}

RFC~8446 (TLS~1.3) \cite{b3} addressed several shortcomings of its predecessors: static RSA key transport (no forward secrecy), renegotiation and weak or susceptible to downgrade: attack cipher suites. Version~1.3 requires ephemeral (EC)DHE key exchange with all handshakes, and only allows a limited set of cipher suites that support authenticated encryption schemes. By default, our system will not allow anything less than TLS~1.3, which means that there is no possibility of downgrade of session-level protection. Our application-layer ratchet initialization is based on HKDF \cite{b4} (RFC5869), which is also used in the TLS~1.3 key schedule, providing separation of the entropy extraction and key expansion.

\subsection{Adaptive and Context-Aware Security}

For example, adaptive bitrate streaming—variations in video quality based on available bandwidth—is a standard practice in network management, and congestion control algorithms continuously adjust the rate on which packets are sent, based on the packet loss observed. A similar feedback principle is not much discussed in the literature in the context of cryptographic policy. The majority of implemented secure messaging systems have fixed key rotation periods, padding policies, and retries. The adaptive engine uses these parameters as outputs of a state machine, where the inputs are actual network and security metrics, so as to provide protection at an appropriate level relative to the threat level measured during runtime instead of worst-case scenarios.

\subsection{Group Messaging Security}

The Messaging Layer Security protocol \cite{b5} also tackles the scalability problem of pairwise encryption for group conversations by proposing a group key agreement scheme (TreeKEM) with a logarithmic number of messages in the number of group members, which is standardized as RFC~9420. The current design is based on a per-client directed encryption loop, suitable for small groups, but not for large deployments. One of the main directions suggested for future work in Section~IX is the extension of the system to MLS-style ratchet trees.

\section{System Architecture}

The system is a two-tiered client-server system. A backup transport path is set up, with a TLS-wrapped TCP socket on port~8080, and a plain UDP socket on port~8081, both of which are bound on the server. The application-layer DH key exchange starts after a TLS handshake on the TCP channel has been completed by the client and the server.

\subsection{Server}

The server is implemented as one long running process in the POSIX model. The \texttt{accept()} loop hangs on the TCP socket; each new connection accepted is detached to a new \texttt{pthread} which performs the TLS handshake, DH key exchange, authentication, message routing, and eventual teardown of that client. Each connection represents a single state, this thread per connection approach provides strict per-client state. There is a limit of \texttt{MAX\_CLIENTS}~=~50 concurrent sessions, and all threads that access the shared client registry will do so in series, through one mutex on \texttt{ClientEntry[50]}.

There are two background threads that run independent from Client connections. Once per second, an adaptive engine thread examines the current metrics structure, and stores the resulting operating mode in a shared variable, EngineState, which is read by all other modules without any locking, with a maximum of 1 tick of latency. A separate thread is used for receiving frames on a UDP socket, and sends each frame through exactly the same 128-bit message-ID deduplication check that occurs on the TCP path before the unique frames are passed to the client handler.

The server will process an incoming chat message, find the destination entry in the client table, and send it to all the active sessions, and broadcast an update of the user list. If the intended recipient is not online when the message is delivered, it is placed in a persistent, on-disk offline queue and is re-delivered, with the message being re-delivered again and re-encrypted by the recipient's current ratchet state when it is reconnected.

\subsection{Client}

Once the authentication is done, every client will execute two threads. The send thread removes messages from a three-level priority queue in priority order, generates the next message key based on the current ratchet, encrypts the padded plaintext using that key and sends the frame simultaneously using TLS/TCP and UDP. The receive thread consumes the message from the TLS socket, verifies the message ID against the local deduplication ring buffer, decrypts the payload and passes it to the UI layer. In the GTK client, the delivery is placed on the main loop using \texttt{gdk\_threads\_add\_idle()}, ensuring that all the mutations of widgets are done on the UI thread; in the CLI client, the receive thread directly writes to the standard output.

\section{Wire Protocol and Connection Lifecycle}

\subsection{Packet Framing and Header Structure}

Each message has a common 28-byte binary header, including a 128-bit \texttt{msg\_id} field for deduplication on both the TCP and UDP delivery paths. All payload messages sent via \texttt{MSG\_CHAT} in the High-Risk mode will be padded so that the total encrypted payload frame is a pre-determined 4,112~bytes: 16~bytes IV (4-byte nonce prefix preceded by 12-byte nonce). This common size of the frame defeats traffic-analysis attacks based on the observation of the packet size to determine the message content or length.

\section{Cryptographic Design}

The security architecture uses multiple cryptographic layers operating in tandem to ensure independent security. The design is not based on any single security method; instead it builds on top of multiple security methods: transport-level security, public-key identity verification, ephemeral session-key establishment, continuous key evolution using Double Ratchet, and message-level symmetric encryption. Fig.~\ref{fig:cryptoarch} shows the entire architecture of this layered design.

\begin{figure}[htbp]
\centering
\includegraphics[width=\columnwidth]{4.png}
\caption{Layered cryptographic architecture of the proposed secure chat system. Six successive layers---TLS\,1.3 transport security, RSA-2048 authentication, X25519 DH key exchange with HKDF, Double Ratchet message-key evolution, AES-256-CBC message encryption, and key and memory hygiene collaborate to provide a secure channel establishment, identity assurance, forward secrecy, break-in recovery, constant-size padded ciphertext, and secure key management respectively.}
\label{fig:cryptoarch}
\end{figure}

The system uses the following four interlocked cryptographic layers:

\begin{enumerate}
    \item \textbf{Session Key Agreement} --- X25519 ECDH~\cite{b7} (\texttt{MSG\_DH\_INIT} / \texttt{MSG\_DH\_RESP}) which establishes a shared secret, which HKDF \cite{b4} then expands into a initial ratchet root and chain keys.
    \item \textbf{Identity Authentication} --- RSA-2048~\cite{b9} signatures over the username bytes to authenticate both parties; the public key is registered on the server at first login and then verified on every subsequent authentication.
    \item \textbf{Transport Confidentiality} --- TLS~1.3 wraps all TCP I/O; OpenSSL is configured to reject TLS~1.2 and earlier, preventing silent protocol downgrade.
    \item \textbf{Message-Level Confidentiality} --- AES-256-CBC~\cite{b8} with per message keys derived from the Double Ratchet chain which provides an end to end encryption that operates inside the TLS tunnel and does not expose message content even if the TLS session is compromised.
\end{enumerate}

\subsection{Double Ratchet Key Evolution}

The Double Ratchet \cite{b1} advances its symmetric ratchet on every message using HMAC-SHA256~\cite{b10}:
\begin{align}
    \text{msg key} &= \text{HMAC-SHA256}(\text{chain key},\ \texttt{0x01}) \\
    \text{new chain key} &= \text{HMAC-SHA256}(\text{chain key},\ \texttt{0x02})
\end{align}
Therefore each message uses a distinct derived key, and the old chain key is discarded immediately after the derivation step. The DH ratchet injects additional Diffie Hellman entropy every \texttt{dh\_ratchet\_freq} messages, providing break in recovery. In High-Risk mode this frequency is set to~1, causing a new X25519~\cite{b7} keypair which is generated for every message and maximizing the rate of key material turnover. All ephemeral key material is erased with \texttt{OPENSSL\_cleanse()} after use.

\section{Adaptive Engine and Intrusion Detection}
\label{sec:adaptive_engine}

\subsection{Three-State Adaptive Engine}

The adaptive engine translates the measured operating conditions into concrete cryptographic and transport parameter changes. Instead of applying a single design time configuration, the engine regularly monitors a set of network and security indicators and rewrites the active parameter set whenever thresholds are crossed. A background daemon thread performs one evaluation cycle per second, collecting telemetry information from all active client sessions and collapsing it into a \texttt{Metrics} structure.

The following are the metrics which are tracked and refreshed on every evaluation cycle:
\begin{itemize}
    \item \texttt{packet\_loss\_rate}: a weighted rolling average calculated over the most recent 100 packets sent.
    \item \texttt{rtt\_ms}: smoothed round trip time maintained using an exponentially weighted moving average (EWMA).
    \item \texttt{auth\_fail\_count}: cumulative count of authentication failures observed from the current IP which is used to detect for brute force activity.
    \item \texttt{replay\_count}: total number of duplicate message IDs which are caught during the current evaluation window.
    \item \texttt{consecutive\_timeouts}: number of consecutive socket level timeout events which are observed for the active sessions.
\end{itemize}

At the end of every one second sampling interval, the engine compares the collected metrics against a pre determined thresholds and selects the appropriate operating state. The system defines three states which are Normal, Unstable, and High-Risk.

\subsubsection{State Transition Logic}
The engine transitions between the different execution modes according to the following rules.

\paragraph{a) High Risk Escalation}
The engine escalates immediately to High Risk mode if any one of the following condition is met:
\begin{itemize}
    \item Rolling packet loss rate (RPLR) is atleast 20\%.
    \item Cumulative authentication failure count (\texttt{auth\_fail\_count}) atleast 5.
    \item Cumulative replay count (\texttt{replay\_count}) atleast 3.
\end{itemize}

\paragraph{b) Unstable Transition}
The engine transitions from Normal to Unstable if the conditions degrade without reaching the High Risk threshold:
\begin{itemize}
    \item Rolling packet loss rate is more than 5\%.
    \item Consecutive socket level timeouts is atleast 3.
\end{itemize}

\paragraph{c) Normal Recovery and Hysteresis}
The engine uses a hysteresis approach: Normal is only downgraded when all of the metrics being monitored are consistently below the corresponding Unstable thresholds for 30 seconds or more.

Each time the state changes, the server sends a control frame to all clients connected, and updates the global variable \texttt{EngineState}. Table~\ref{tab:aprm} shows the parameter changes for each state. In the case of lossy network conditions, the resulting lower crypto chunk sizes and higher retry budgets give significantly higher delivery rates than the Normal-mode configuration.

In High-Risk mode, three extra defenses are turned on:
\begin{itemize}
    \item \textbf{Forced Padding}: All message payloads are padded with a uniform 4,096~bytes to prevent the observer from inferring message length from packet size.
    \item \textbf{Randomized Retry Delay}: Retransmissions are delayed by a random interval of 100 - 500\,ms, which can make timing based traffic analysis more difficult.
    \item \textbf{Aggressive DH Ratcheting}: The DH ratchet executes on every message (\texttt{dh\_ratchet\_freq}~=~1), this maximizes forward secrecy and post compromise recovery speed.
\end{itemize}

\subsection{Intrusion Detection System}

The server has a light weight stateful intrusion detection subsystem (IDS) that protects against authentication brute forcing and packet replay attacks. The IDS stores all the tracked IPs in a statically allocated tracking table that has a maximum size of \texttt{MAX\_BLOCKED\_IPS} and provides constant-time per-packet operation.

The tracking table contains the following entry for each record:
\begin{itemize}
    \item IP address of the client making the request (string up to 48 characters).
    \item A counter which keeps the count of failed authentications from that address.
    \item A boolean that can be set to true if the IP is blocked or false otherwise.
    \item A time stamp that indicates the time of block application.
\end{itemize}

The IDS provides two reporting interfaces: \texttt{ids\_record\_auth\_fail()} and \texttt{ids\_record\_replay()}. If an authentication attempt fails such as when an invalid RSA signature is received or a client attempts to sign a username that has an active session, the IDS will increase the failure counter for that IP. Once the counter is equal to ~5, then the next sequence runs automatically:
\begin{enumerate}
    \item The IP address is added to a blocked list.
    \item The current epoch time is recorded as the block timestamp.
    \item \texttt{metrics\_record\_auth\_fail()} is called which triggers immediate escalation of the adaptive state machine to High Risk mode.
\end{enumerate}

A replay attack is treated similarly: if an ID is found in the deduplication ring buffer, the event is considered a replay attempt and the engine is put into High-Risk mode with \texttt{metrics\_record\_replay()}. Blocked IPs are applied within the server's \texttt{accept()} loop, so that if an IP address is blocked, the connection will be dropped before the TLS~1.3 handshake, saving CPU cycles. Block expiry is done lazily, no dedicated timer thread: \texttt{ids\_expire\_blocks()} is called each time a message is received, and if the time elapsed since an IP's block timestamp has passed 300~seconds (5~minutes) the block flag is turned off and the tracking record is reset.

All blocking and unblocking operations are recorded in a special IDS log file in the following format:
\begin{verbatim}
[IDS 2026-06-10 14:23:01] BLOCK from 192.168.1.50
[IDS 2026-06-10 14:28:01] UNBLOCK 192.168.1.50
\end{verbatim}

\section{Multipath Transport and Offline Queue}
\label{sec:multipath_transport}

\subsection{Dual-Path Delivery and Deduplication}

When the network is not stable or friendly, the system resorts to a simultaneous dual-path delivery mechanism: each outgoing message is delivered simultaneously via a primary path with TLS~1.3 over TCP socket and a redundant path via another UDP datagram. The client send loop will adhere to any retry budget set by the adaptive engine, encrypting each frame and sending it over the TLS socket as well as dispatching the same ciphertext as a UDP datagram. The engine delays the retransmission of the following packet by a random 100--500\,ms in High-Risk mode, making timing-based traffic analysis more difficult, while in Normal and Unstable modes the retransmission interval is fixed. Messages that are set to Critical priority will be sent with 2 more retries than the default number, to ensure that as many messages as possible are delivered.

Both paths can produce the same frame, so the receiver must ensure that it doesn't process them twice. The receiving pipeline will have a thread-safe deduplication mechanism that uses a circular buffer (circular buffer definition follows):
\begin{verbatim}
dedup_buf[1024][16]
\end{verbatim}
This ring buffer can store up to 1024 message IDs of 128-bits each. The receiver calls \texttt{dedup\_check()} on each incoming frame: If the message ID is already in the active window, the frame is silently discarded; otherwise \texttt{dedup\_add()} appends the ID (advancing the ring buffer pointer modulo 1,024) and forwards the payload for decryption. All deduplication operations are serialized serializing with a \texttt{pthread\_mutex\_t} and both lookup and insert take constant time to not become a throughput bottleneck.

\subsection{Client-Side Priority Queue}

The client transmission pipeline consists of a three level priority scheduling mechanism for outgoing messages. Messages are classified into one of three priority levels:
\begin{itemize}
    \item \textbf{Normal (Priority~0)}: Processed in normal FIFO order.
    \item \textbf{Urgent (Priority~1)}: Queued ahead of Normal traffic with reduced propagation delay.
    \item \textbf{Critical (Priority~2)}: This is assigned as the highest scheduling priority and is placed at the head of the queue.
\end{itemize}
When a Critical message is enqueued, the client calls \texttt{pthread\_cond\_signal()} to wake the send thread immediately if it is idle or blocked. Critical messages also receive extra retry attempts in the multipath delivery loop. Priority designations are carried across the network via the \texttt{MsgHeader.priority} field.

\subsection{Persistent Offline Message Queue} %Here

If a message is sent to someone who is not on-line, the server delivers the message asynchronously through a persistent, on-disk, offline queue. The server's client handler makes the following undeliverable messages to the recipient's queue directory:
\begin{verbatim}
data/offline_queue/<username>/
\end{verbatim}
The server runs a tight regular expression (\texttt{[a-zA-Z0-9\-]}) to check the username before accessing any filesystem, to avoid directory traversal attacks involving embedded path separators like \texttt{/../}. Directories are opened with the permission of 0700 and message files with the permission of 0600, thus enforcing access control at the OS-level. Each message goes into a file named \texttt{<timestamp\_ms>\_<msg\_id\_hex>} and the queue is read in lexicographical order on reconnection, thus maintaining the chronological ordering of the messages.

It was decided that the messages will not be ciphertexts on the server but will be stored as plain text. If the pre-encrypted messages were encrypted with the current ratchet state of the recipient, then the recipient's ratchet state at the time of the queuing would not be known until reconnection, which would lead to problems with synchronization and make the queued messages unreadable on reconnection. Messages are instead protected at rest by OS-level access control permissions, and re-encrypted under the recipient's live ratchet state at the time of delivery. These frames are flagged as \texttt{MSG\_FLAG\_IS\_OFFLINE\_REPLAY} and replayed frames are distinguished from live frames on the client UI by displaying an indicator that the frame has been queued for replay. There is an offline queue of maximum \texttt{OFFLINE\_QUEUE\_MAX}~=~500 messages per user, and once this limit is reached the extra messages are dropped.

\section{Evaluation}
\label{sec:evaluation}

This section presents the empirical testing of the proposed system in terms of cryptographic correctness, multi-path transport resilience and responsiveness of the adaptive security engine.

\subsection{Experimental Setup}

Experiments were carried out in a containerized setup simulating various real clients and a server. The network degradation was added to the client-server loopback interface with the help of the Linux Traffic Control (\texttt{tc}) utility and the network emulation module called \texttt{netem}. Brute-force password and packet replay authentication injectors cause security-related events.

\subsection{Cryptographic and Functional Verification}

The cryptographic properties mentioned in Section~V have been tested empirically under normal operating conditions:
\begin{itemize}
    \item \textbf{Key Uniqueness \& Integrity:} All derived symmetric keys were confirmed as unique, for 100 consecutive keys derived from the same message key. The following is a round trip test to AES-256-CBC using the same plaintexts which recovers the same plaintexts in each case.
    \item \textbf{Forward Secrecy:} The client active ratchet state was removed at message~50. Attempts to decrypt historical messages (1 - 49) all failed, thus establishing that if a message is compromised, past traffic is not exposed.
    \item \textbf{Post-Compromise Security (Break-in Recovery):} The symmetric chain key was compromised, starting at message~50. After the next DH ratchet exchange (every 10 messages in Normal mode and every message in High Risk mode), the attacker failed to decrypt any further messages, confirming that the messages have been recovered for a break-in.
    \item \textbf{Traffic Analysis Mitigation:} Using \texttt{tcpdump} in High-Risk mode, it was observed that the actual message content had no effect on the length of the \texttt{MSG\_CHAT} payload, which was always 4,112~bytes (16-byte IV + 4,096-byte ciphertext).
\end{itemize}

\subsection{IDS Metrics and Adaptive Engine}

The transitions and operating parameters of the adaptive engine has been verified under the following conditions:
\begin{itemize}
    \item \textbf{Packet Loss ($\ge$ 5\%):} Triggers a change from Normal to Unstable mode. (Status: Pass)
    \item \textbf{Packet Loss ($\ge$ 20\%):} Transitions to Unstable to High-Risk. (Status: Pass)
    \item \textbf{Authentication Failures ($\ge$ 5 from the same IP):} Induces a rapid switch to High-Risk mode from all other modes. (Status: Pass)
    \item \textbf{Replay Attacks ($\ge$ 3 detections):} Causes state to switch to High-Risk mode immediately from any state. (Status: Pass)
    \item \textbf{Metrics Stability ($\ge$ 30 seconds below Unstable thresholds):} Changes back to Normal mode. (Status: Pass)
\end{itemize}

\subsection{Other System Behaviors}

\begin{itemize}
    \item \textbf{Multi-Path Deduplication:} When performing packet loss injection, the same messages were received along both TLS/TCP and UDP paths. The 1024 entry ring buffer was able to correctly identify and suppress all duplicate messages and send each unique one to the application layer once.
    \item \textbf{Intrusion Blocking:} Five failed authentication attempts by a single IP resulted in blackholing of the host by the IDS. All subsequent connection attempts were aborted before TLS handshake, as expected, saving cpu resources.
    \item \textbf{Offline Replay:} Offline users' messages were stored in a queue on disk in order. When the client reconnected, the server re-encrypted and sent the queued frames, with the \texttt{MSG\_FLAG\_IS\_OFFLINE\_REPLAY} flag set, and client successfully rebuilt the chat history in the right sequence.
\end{itemize}

\section{Limitations and Future Work}

The proposed system clearly describes a multi-layered security system, but there are some drawbacks in the existing design that need to be discussed clearly and systematically in the future.

\subsection{Trusted Server Relay and the Limits of End-to-End Encryption}

The biggest architectural constraint is the requirement for a trusted server relay for message relaying. The server completely decodes each received message with its own receive context, and gets the desired recipient identifier from the plaintext payload, before re-encrypting the resulting plaintext message with its send-ratchet context before forwarding it. The server-visible decryption is a necessary architectural feature of the current recipient-resolution design, and the system does not have the strict end-to-end encryption semantics as used in the academic sense: the system temporarily decryption-reveals message plaintexts to the server. It's a conscious design tradeoff that greatly reduces the complexity of offline message queuing, adaptive priority routing, and server-side session management, but it's a pretty significant break from the security model of fully end-to-end encrypted applications like Signal, which only send Opague Ciphertexts over the internets. If an adversary were able to compromise the server infrastructure, they would only have a short time to have access to message plaintexts in the forwarding window. Further research is needed to examine a pre-key distribution architecture where pre-keys are signed by recipients and uploaded to a server, so that the sender can simply encrypt to the recipient's pre-key without needing to decrypt anything on the server. Sealed-sender is a well-defined reference design for this capability, and the X3DH key agreement protocol \cite{b6} provides another.

\subsection{Offline Message Storage Security}

Currently, the message queue is being stored as plain text in the server's persistent storage in the offline mode. Exposure risk is minimized by the OS level access control permission and by the per-user retention limit, however, no at-rest encryption means that if the server storage infrastructure were to be compromised, whether that be because of access control failure, physical media theft, or a compromise of the backups, all queued messages might be exposed. Future designs should include the option of using keying material derived from the recipient for the purposes of encrypting messages that are queued to the recipient and only the recipient will know the secret key when they reconnect to the server again. If this method is used in conjunction with X3DH pre-key distribution, then there will be no exposure in the offline delivery path in plaintext.

\subsection{Identity Management and Public-Key Infrastructure}

The existing identity system is adequate for localized deployments with limited user base and the ability to centrally manage trust. During user registration, each user claims to be his/her own RSA public key, without relying on a certificate authority or revocation system or a web-of-trust structure. The model has significant drawbacks for large scale or open membership deployments, because there is no guarantee that a public key presented by a user is for their claimed identity: if they are presenting it for a long time, there is the potential for adversarial impersonation. Further, without the key revocation, a broken identity key cannot be invalidated without an out-of-band coordination. Future work needs to test certificate-based trust models, decentralized key-transparency logs~\cite{b13}, and key-management infrastructures enough to achieve wider interoperability and revocation needs.

\subsection{Scalability and Group Communication}

The current architecture is only suitable for pairwise directed messaging: the server will process the members one by one, which results in linear growth of processing time and bandwidth as the number of members in the group increases. New, explicit group key management protocols with sublinear complexity, like the MLS protocol \cite{b5} (RFC~9420) that use a tree-based key management structure, should be considered as extensions to the current architecture, with an overhead of O(log~$n$) per message.

\subsection{Adaptive Security Mechanisms and Threat Intelligence}

The existing adaptive engine is based on low-level heuristic information like packet losses and authentication anomaly counters. Does not include more context intelligence in contemporary deployments. More detailed analyses of the behavior, peer-reputation scoring, and machine learning-based threat classification should be explored to allow for more adaptive security measures to be taken in the future while minimizing false escalations that add cryptographic overhead to the legitimate users.

\subsection{Formal Verification}

It is not actually analysed with a symbolic model checker (e.g. ProVerif~\cite{b11} and Tamarin~\cite{b12}) and neither is it analysed using a computational proof framework with the protocol, but rather security at the design and architecture level. Formal verification is regarded as best practice for cryptographic protocols and has become a requirement for high assurance deployments increasingly from standards bodies. Future research is needed to formally model and mechanize the major security properties that the protocol guarantees, such as forward secrecy, break in recovery, and authentication soundness.

\section{Conclusion}

This key idea is that configuration and cryptographic operations are a function of the operating conditions measured, rather than being fixed. One specific example of achieving that goal is the three-state adaptive engine, which reads metrics about the network and security events detected by the IDS, and immediately propagates mode changes to any module that interacts with encryption or delivery. In High-Risk conditions, the adversary that has caused the escalation, by replay injection or authentication probing, will be able to rotate the Diffie--Hellman key on each and every message, embed the length of the plaintext into the length of the ciphertext (making both look uniformly sized), and introduce random delays into the retries without the involvement of any operator.

Experimental testing has shown that the state transitions at the stated thresholds and that there is a thirty-second hysteresis window that ensures that the downgrade is not triggered early under borderline loss rates. It is empirically proven to support ratchet forward secrecy and break-in recovery and it is proven at packet capture level to enforce constant-payload-size. Passes all 13 functional tests.

The most important architectural constraint, namely that the server must decrypt each message in memory to route and re-encrypt it, leaving the server as a trusted relay, hasn't been addressed. To solve this problem, we need to use X3DH pre-key exchange~\cite{b6} and the server will send encrypted blobs without ever having seen plaintext. The second near-term priority is extending the per-client encryption loops to a proper group ratchet mechanism similar to MLS~\cite{b5}. There are clear paths in both directions that develop directly on existing cryptographic infrastructure.
