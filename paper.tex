\begin{abstract}
Static security configurations cannot adapt to evolving threat scenarios, which compromises secure messaging on networks that aren't reliable and trustworthy. We introduce an application layer Signal protocol Double Ratchet, transport layer TLS 1.3, and a three state adaptive engine, which can reconfigure application-layer cryptographic parameters and transport-layer parameters based on live network metrics, and any detected security events. A lightweight per IP intrusion detection system will report replay and authentication failures directly into the engine state machine, thus automatically switching to Unstable or High Risk mode. All payloads are padded to a fixed size of 4096 bytes, DH ratchet steps are used on every payload and randomized retry delays defeat traffic analysis in High Risk mode. It offers forward security and break in security recovery as per the Double Ratchet specification, multipath deduplication through 128 bit message ID ring buffer and persistent offline delivery of messages. All 13 functional tests pass for evaluation of correct state transitions for both injected packet loss and authentication failure conditions.
\end{abstract}

\section{Introduction}

In the last decade, secure messaging has been a mandatory feature in both civilian and enterprise, as well as operational, communication environments. A lot has happened in the cryptographic primitives of these systems: Transport Layer Security version~1.3~\cite{b3} adds authenticated encryption with forward secrecy at the session level, and application-layer protocols like the Signal Double Ratchet~\cite{b1} bring that at the per-message level. Less focus has been paid to the connection between the environment in which a system operates and their level of security. Most of the systems that are deployed use a fixed cryptographic configuration that are designed at the system design time and then assumed to remain as designed, regardless of what the network or the adversary does.

This assumption is violated in reality. A link that is in 20\% packet loss should have a different retry behaviour than a healthy link, a session that is denied a packet by an active authentication brute force should have tighter key rotation, and a denial of a packet at this layer means blocking at IP level, etc. This distinction can't be captured in a static configuration. The outcome is a permanently posture-d for worst case with extra overhead in normal cases or a permanently posture-d for common case with underdefending in bad ones.

This paper introduces a multi-client end-to-end encrypted chat system realized in C~(C11, POSIX), in which the security posture is considered as a runtime variable. It includes a TLS~1.3 transport encryption, a Signal-style Double Ratchet at the application layer, simultaneous dual-path delivery across TCP and UDP, and a three-state adaptive engine that's fed by both the network quality metrics and a co-resident per-IP intrusion detection system~(IDS). If the engine senses that the quality is deteriorating (due to increased packet loss, replay detection, or increasing number of authentication failures from a single address), it will increase its mode of operation and immediately reconfigure cryptographic and transport parameters for each active session. The recovery to the baseline mode is hysteretic, meaning that the metrics have to be stable for a minimum of 30 seconds, to prevent oscillatory behavior at the borderline.

The main contribution of this work are as follows:
\begin{enumerate}
    \item An adaptive engine with 3 states (Normal, Unstable, High Risk) based on a rolling packet loss rate, smoothed round-trip time, per-session authentication failure count, and cumulative replay detection count.
    \item TLS support of the Signal Double Ratchet at the applica tion layer with per-message forward secrecy and break-in recovery without relying on the underlying TLS session state.
    \item Simultaneous delivery over both TCP and UDP with deduplication in a 128-bit message-ID ring buffer, which guarantees delivery resilience in case one of the trans port paths is lost.
    \item A light weight per IP IDS that routes security events directly into the adaptive state machine, reducing threat detection and adaptive cryptographic response to a single feed back loop.
    \item When the client reconnects, offline message queue with timestamp ordered replay, while hiding the ratchet state from it and allowing asynchronous delivery.
\end{enumerate}

The rest of this paper is organized as follows. In section~II related work is surveyed. This section - III describes the overall system architecture. The wire protocol and cryptographic design is described in Sections~IV and~V respectively. Sections~VI and~VII discuss the adaptive engine with IDS coupling and the multipath transport using offline queuing. Evaluation results are given in Section~VIII, limitations and future directions in Section~IX, and a conclusion in Section~X.

\section{Related Work}

\subsection{End to End Messaging Protocols}

Signal Double Ratchet Algorithm~\cite{b1} has been the most popular construction of asynchronous end-to-end encrypted messaging. Instead of the previous session based schemes, which gave the same key for the whole conversation, the Double Ratchet protocol uses two tightly coupled ratchet functions: a symmetric ratchet that chops a new key for each message, and a Diffie Hellman ratchet that periodically introduces new entropy via a new ephemeral key exchange. The combination guarantees that if an attacker retrieves the state of the chain at any time, the attacker will not be able to generate keys for messages from an epoch other than the current epoch. The first rigorous security proof, which proved forward secrecy and post compromise security to be formally provable properties, was given by Cohn-Gordon et al.~\cite{b2}. We strictly adhere to the Double Ratchet specification, but introduce DH ratchet frequency as an adaptive parameter which allows the engine to raise key turnover under threatening circumstances.

\subsection{Transport Layer Security}

In RFC~8446, TLS~1.3~\cite{b3} removed several weaknesses inherited from previous versions: the static RSA key transport (which has no forward secrecy), negotiable cipher suites including those known to be weak, and a renegotiation mechanism, which added side-channel risk. Version~1.3 requires ephemeral (EC)DHE key exchange for all handshakes, and only a few cipher suites which support authenticated encryption schemes. Our system does not allow any version less than 1.3 of OpenSSL to be used, so that the protection of the session level cannot be downgraded silently. Like two other extensions we use, TLS~1.3 key schedule and our application-layer ratchet initialization rely on HKDF~\cite{b4} which is defined in RFC~5869 for a clean separation of entropy extraction and key expansion.

\subsection{Adaptive and Context-Aware Security}

Adjusting system behaviour in response to measured environmental conditions is a well-known practise in network management in adaptive bitrate streaming the video quality adapts to the capacity of the link, and in congestion control algorithms the transmission rate is adjusted continually in response to measurements taken. The same feedback principle has been addressed much less in the literature with regard to cryptographic policy. The vast majority of deployed secure messaging systems set the number of retries, padding policy and key rotation timers as fixed values. We use these as outputs of a state machine that takes inputs from live network and security metrics instead of worst case assumptions, thus respecting the principle of least privilege in line with the current threat level.

\subsection{Group Messaging Security}

The Messaging Layer Security protocol~\cite{b5}, which is standardized as RFC~9420, addresses the scalability limitations of pairwise key establishment for group conversations through a tree structured key agreement scheme (TreeKEM) that achieve logarithmic message complexity in the number of group members. Our current design handles broadcast as a loop of directed per client encryptions, which is functionally correct for small groups but does not scale for larger deployments. Extending the system to MLS style group ratcheting is identified in Section~IX as the primary direction for future work.

\section{System Architecture}

The system follows a two-tier client-server architecture. The server listens on TCP
port~8080 (primary, TLS-wrapped) and UDP port~8081 (backup path). Clients connect over
both transports simultaneously after the TLS handshake completes on the TCP channel.

\subsection{Server}

The server is a single long-running POSIX process. An \texttt{accept()} loop blocks on
the TCP socket; each accepted connection is handed to a newly spawned detached
\texttt{pthread} executing \texttt{handle\_client()}, which manages the TLS handshake,
DH key exchange, authentication, message routing, and eventual cleanup for that client.
This thread-per-connection model isolates per-client state while supporting up to 50
concurrent sessions (\texttt{MAX\_CLIENTS}). All threads that read or write the client
registry share a single \texttt{pthread\_mutex\_t} that serializes access to the
\texttt{ClientEntry[50]} table.

Two background threads run independently of client connections. The adaptive engine
thread evaluates the rolling \texttt{Metrics} structure once per second and writes the
current operating mode to a shared \texttt{EngineState} variable; all other modules
read this variable without acquiring a lock, tolerating at most a one-tick lag. A
dedicated UDP receiver thread drains the UDP socket continuously, subjects each received
frame to the same 128-bit message-ID deduplication check used on the TCP path, and
forwards unique frames to the appropriate client handler.

When a client disconnects, the server removes the corresponding entry from the client
table and broadcasts an updated user list to all remaining sessions. Messages sent to a
recipient who is offline at delivery time are written to the persistent offline queue
and delivered—re-encrypted with the recipient's current ratchet state—upon reconnect.

\subsection{Client}

Two client implementations are provided: a GTK3 graphical client and a command-line
client. Both share the same underlying networking and cryptographic modules and differ
only in their presentation layers.

Each client runs two threads after authentication completes. The \emph{send thread}
dequeues outgoing messages from the three-level priority queue in priority order,
derives the next message key from the ratchet, encrypts the padded plaintext under
AES-256-CBC, and transmits the resulting frame over both the TLS/TCP and UDP paths.
The \emph{receive thread} reads from the TLS socket, checks the message ID against the
local deduplication ring buffer, decrypts the payload, and delivers it to the UI layer.
In the GTK client, delivery is posted to the GTK main loop via
\texttt{gdk\_threads\_add\_idle()} so that all widget mutations occur on the UI
thread. In the CLI client, the receive thread writes directly to standard output.

\section{Adaptive Engine and Intrusion Detection}
\label{sec:adaptive_engine}

\subsection{Three-State Adaptive Engine}

A dynamic adaptation mechanism continually adjusts system behavior to prevailing network conditions and security events, ensuring both communication reliability and confidentiality. Rather than relying on a static, design-time configuration, the system dynamically alters transport and cryptographic properties at runtime based on real-time observations. The core of this framework is a background daemon thread running on the server that evaluates telemetry and security metrics once per second. During each evaluation cycle, the engine collects and aggregates telemetry data from all active client sessions into a shared \texttt{Metrics} structure.

The following parameters are continuously monitored and updated:
\begin{itemize}
    \item \texttt{packet\_loss\_rate}: A rolling weighted average of packet loss calculated over the last 100 transmissions.
    \item \texttt{rtt\_ms}: The smoothed round-trip time, calculated using an Exponentially Weighted Moving Average (EWMA).
    \item \texttt{auth\_fail\_count}: A counter monitoring failed authentication attempts to detect unauthorized access or brute-force activities.
    \item \texttt{replay\_count}: The cumulative count of duplicate message replays detected during execution.
    \item \texttt{consecutive\_timeouts}: The consecutive socket-level timeout occurrences recorded for active transactions.
\end{itemize}

At the end of each one-second sampling period, the engine compares the collected metrics against predefined operational thresholds to transition the system to the optimal execution state. The system defines three execution modes: Normal, Unstable, and High-Risk.

\subsubsection{State Transition Logic}
The engine transitions between execution modes based on network and security state indicators.

\paragraph{High-Risk Escalation}
The engine immediately escalates to High-Risk mode if any of the following conditions are met:
\begin{itemize}
    \item The rolling packet loss rate (RPLR) reaches or exceeds 20\%.
    \item The cumulative authentication failure count (\texttt{auth\_fail\_count}) reaches 5 or more.
    \item The cumulative replay detection count (\texttt{replay\_count}) reaches 3 or more.
\end{itemize}

\paragraph{Unstable Transition}
The system transitions from Normal to Unstable mode if the network conditions degrade without meeting the High-Risk threshold:
\begin{itemize}
    \item The rolling packet loss rate exceeds 5\%.
    \item The connection records three or more consecutive socket-level timeouts.
\end{itemize}

\paragraph{Normal Mode and Hysteresis}
To prevent rapid, oscillatory state transitions under borderline conditions, the engine employs a hysteresis mechanism. The system will only downgrade to Normal mode after all monitored metrics remain consistently below their respective Unstable thresholds for a continuous window of 30 seconds.

Upon any state transition, the server broadcasts an \texttt{MSG\_ENGINE\_STATE} control frame to all connected clients and updates the global variable \texttt{EngineState}. The configuration adjustments corresponding to each state are presented in Table~\ref{tab:adaptive_params}.

Under degraded network conditions, combining smaller cryptographic chunk sizes with increased retry budgets significantly enhances delivery success rates over lossy links. In High-Risk mode, additional defensive mechanisms are enabled:
\begin{itemize}
    \item \textbf{Forced Padding:} All message payloads are padded to a uniform size of 4,096 bytes to thwart traffic analysis and hide length side-channels.
    \item \textbf{Randomized Timing Delay:} Retries are subject to randomized delays between 100\,ms and 500\,ms, complicating timing-based attacks.
    \item \textbf{Aggressive DH Ratcheting:} A Diffie-Hellman ratchet step is executed on every message to achieve maximum forward secrecy and speed up post-compromise recovery.
\end{itemize}

\subsection{Intrusion Detection System}

The server incorporates a lightweight, stateful Intrusion Detection System (IDS) to detect authentication brute-forcing and packet replay attacks. To defend against resource exhaustion and Denial-of-Service (DoS) attacks targeted at the tracking subsystem, the IDS maintains a statically allocated tracking table of size \texttt{MAX\_BLOCKED\_IPS}. Lookup operations in this table are optimized using a fast lookup strategy that minimizes per-packet processing overhead.

Each tracking record in the table stores:
\begin{itemize}
    \item The client IP address (stored as a string, maximum 48 characters).
    \item An authentication failure counter.
    \item A boolean block status flag.
    \item A timestamp indicating when the IP block was instituted.
\end{itemize}

The IDS exposes two primary reporting interfaces: \texttt{ids\_record\_auth\_fail()} and \texttt{ids\_record\_replay()}. 

If an authentication attempt fails—such as when an invalid RSA signature is received or a client requests a username currently registered to another active session—the IDS increments the failure counter for that IP. Once this counter reaches 5, the following sequence occurs automatically:
\begin{enumerate}
    \item The IP address is added to the blocked IP list.
    \item The current epoch time is recorded as the block timestamp.
    \item The engine calls \texttt{metrics\_record\_auth\_fail()}, triggering immediate escalation of the adaptive state machine to High-Risk mode.
\end{enumerate}

Replay attacks are handled analogously. If an incoming message ID matches a record already present in the deduplication ring buffer, the message is classified as a replay attempt. The system immediately invokes \texttt{metrics\_record\_replay()} to transition the adaptive engine to High-Risk mode.

To enforce these security decisions, the server calls \texttt{ids\_is\_blocked(ip)} during the connection \texttt{accept()} loop. If the IP address is blocked, the server immediately drops the connection before initiating the TLS 1.3 handshake, saving CPU cycles. 

To avoid the overhead of dedicated background timer threads, block expiration is managed passively. The function \texttt{ids\_expire\_blocks()} is executed in the server's main loop after processing each incoming message. If the elapsed time since an IP's block timestamp exceeds 300 seconds (5 minutes), the block flag is cleared and the IP tracking record is reset. 

All blocking and unblocking actions are recorded in a dedicated IDS log file using the following format:
\begin{verbatim}
[IDS 14:23:01] BLOCK 192.168.1.50
[IDS 14:28:01] UNBLOCK 192.168.1.50
\end{verbatim}

\section{Multipath Transport and Offline Message Queue}
\label{sec:multipath_transport}

\subsection{Dual-Path Delivery and Deduplication}

To enhance transmission reliability under unstable and adversarial network conditions, the system implements a simultaneous dual-transport delivery strategy. Every outgoing message is transmitted over two separate channels: a primary TCP socket wrapped with TLS 1.3 encryption, and a secondary UDP datagram channel for redundant path delivery.

The client transmission loop adheres to the retry budget (\texttt{max\_retries}) configured by the adaptive engine. During transmission, the sending thread writes the encrypted payload to the active TLS socket and simultaneously sends an identical copy as a UDP datagram. When operating in High-Risk mode, the adaptive engine inserts a random delay of 100\,ms to 500\,ms between retry attempts to complicate traffic timing analysis. Under Normal and Unstable modes, a fixed retry interval is maintained. Messages designated with Critical priority automatically receive two additional retry attempts beyond the baseline limit to maximize delivery probability.

Because frames are transmitted over both channels, the receiver is expected to receive duplicate packets. To prevent duplicate payloads from reaching the application or user interface layers, the receiving pipeline utilizes a thread-safe deduplication mechanism. The receiver maintains a circular deduplication buffer declared as:
\begin{verbatim}
dedup_buf[1024][16]
\end{verbatim}
This ring buffer stores up to 1,000 message identifiers (\texttt{msg\_id}). For every incoming frame, the receiver invokes \texttt{dedup\_check()} to perform a lookup:
\begin{itemize}
    \item If the message ID is present in the active deduplication window, the frame is silently discarded.
    \item If the ID is not found, the receiver appends it using \texttt{dedup\_add()}, updates the ring buffer pointer (modulo 1024), and forwards the payload for decryption and processing.
\end{itemize}
All deduplication operations are protected by a \texttt{pthread\_mutex\_t} lock to ensure thread safety across concurrent reception paths. The lookup and insertion routines operate in constant time, preventing the deduplication layer from becoming a performance bottleneck.

\subsection{Client-Side Priority Queue}

The client transmission pipeline employs a three-level priority scheduling mechanism to manage outgoing traffic. Outgoing messages are categorized into one of three priority levels:
\begin{itemize}
    \item \textbf{Normal (Priority 0):} Processed in standard First-In, First-Out (FIFO) order.
    \item \textbf{Urgent (Priority 1):} Enqueued ahead of Normal traffic to minimize propagation delay.
    \item \textbf{Critical (Priority 2):} Assigned the highest scheduling priority and placed at the head of the transmission queue.
\end{itemize}

Upon enqueuing a Critical message, the client invokes \texttt{pthread\_cond\_signal()} to immediately wake the transmission thread if it is idle or blocked. In addition to high-priority queue scheduling, Critical messages are granted two extra transmission attempts in the multipath delivery loop to assist propagation in degraded environments. Priority designations are preserved across the network path via the \texttt{MsgHeader.priority} field.

\subsection{Persistent Offline Message Queue}

For asynchronous delivery to disconnected recipients, the server implements a persistent, disk-based offline queuing mechanism. When the server client handler fails to route a message to an offline user, the message is serialized and written to the user's queue directory at:
\begin{verbatim}
data/offline_queue/<username>/
\end{verbatim}

Prior to any filesystem interaction, the server validates the username against a strict regular expression:
\begin{verbatim}
[a-zA-Z0-9_-]
\end{verbatim}
This validation prevents directory traversal attacks (such as injecting path separators like \texttt{/..}). The queue directories and message files are created with restricted permissions—mode \texttt{0700} for directories and \texttt{0600} for files—enforcing operating system-level access control.

Each message is saved as an individual file named using the pattern:
\begin{verbatim}
<timestamp_ms>_<msg_id_hex>
\end{verbatim}
This naming convention allows the server to read the queue files in lexicographical order upon client reconnection, preserving the chronological sequence of the messages.

A critical design choice is storing offline messages in plaintext rather than ciphertext on the server. Because the recipient's future ratchet state cannot be predicted at queuing time, encrypting the message with the current ratchet state would lead to synchronization failures (ratchet desynchronization) upon reconnection, rendering the message undecryptable. Instead, messages are secured on-disk via OS-level access control permissions and encrypted using the recipient's fresh ratchet state established upon reconnection.

Replayed offline messages are transmitted to the client as standard \texttt{MSG\_CHAT} frames, with the \texttt{MSG\_FLAG\_IS\_OFFLINE\_REPLAY} flag set in the header. The client UI uses this flag to display a \texttt{[queued]} indicator, distinguishing replayed messages from live traffic. To prevent storage exhaustion, offline queues are capped at 500 messages per user (\texttt{OFFLINE\_QUEUE\_MAX}); subsequent incoming messages for a full queue are discarded.

\section{Evaluation}
\label{sec:evaluation}

This section details the empirical evaluation of the proposed system, focusing on cryptographic strength, multi-path transport resilience, and the responsiveness of the adaptive security engine.

\subsection{Experimental Setup}

Experiments were carried out in a containerized environment which replicated multiple real clients and a server. Network degradation (packet loss) was injected on the client-server loopback interface using the Linux Traffic Control (\texttt{tc}) utility combined with the network emulation module (\texttt{netem}). Security-related metrics were triggered by script-driven authentication brute-force and packet replay injectors.

\subsection{Cryptographic and Functional Verification}

The cryptographic properties described in Section~V were tested empirically under standard operating conditions:
\begin{itemize}
    \item \textbf{Key Uniqueness \& Integrity:} All derived symmetric keys were verified as unique when evaluated over 100 sequentially generated message keys. A round-trip test using AES-256-CBC successfully recovered the exact plaintexts in all cases.
    \item \textbf{Forward Secrecy:} The client-side active ratchet state was deleted at message 50. Subsequent attempts to decrypt historical messages (1--49) were unsuccessful, validating that compromised keys do not expose past traffic.
    \item \textbf{Post-Compromise Security (Break-in Recovery):} To simulate key compromise, the symmetric chain key was exposed at message 50. Following the next Diffie-Hellman ratchet exchange (occurring every 10 messages in Normal mode and every message in High-Risk mode), the attacker was unable to decrypt subsequent messages, verifying break-in recovery.
    \item \textbf{Traffic Analysis Mitigation:} Packet captures via \texttt{tcpdump} in High-Risk mode confirmed that the size of the \texttt{MSG\_CHAT} payload was consistently 4,112 bytes (16-byte IV + 4,096-byte ciphertext), regardless of the actual message content.
\end{itemize}

\subsection{IDS Metrics and Adaptive Engine}

The adaptive engine's transitions and operational parameters under various conditions were verified:
\begin{itemize}
    \item \textbf{Packet Loss ($\ge$ 5\%):} Prompts the system to transition from Normal to Unstable Mode. (Status: Pass)
    \item \textbf{Packet Loss ($\ge$ 20\%):} Prompts the system to transition from Unstable to High-Risk Mode. (Status: Pass)
    \item \textbf{Authentication Failures ($\ge$ 5 from the same IP):} Prompts an immediate transition from any state to High-Risk Mode. (Status: Pass)
    \item \textbf{Replay Attacks ($\ge$ 3 Detections):} Prompts an immediate transition from any state to High-Risk Mode. (Status: Pass)
    \item \textbf{Metrics Stability ($\le$ 30 seconds):} Triggers a transition back to Normal Mode. (Status: Pass)
\end{itemize}

\subsection{Other System Behaviors}

\begin{itemize}
    \item \textbf{Multi-Path Deduplication:} Under packet loss injection, identical messages were received on both the TLS/TCP and UDP paths. The 1024-entry ring buffer correctly identified and eliminated duplicates, delivering the unique message to the application layer exactly once.
    \item \textbf{Intrusion Blocking:} Exceeding five authentication failures from a single IP prompted the IDS to blackhole the host. Subsequent connection attempts were dropped before initiating the TLS handshake, conserving CPU cycles.
    \item \textbf{Offline Replay:} Messages sent to disconnected users were queued on disk in chronological order. Upon client reconnection, the server re-encrypted and transmitted the queued payload with the \texttt{MSG\_FLAG\_IS\_OFFLINE\_REPLAY} flag set. The client successfully reconstructed the chat logs chronologically.
\end{itemize}

\section{Conclusion}

The central premise of this work is that cryptographic and transport configuration
should be a function of measured operating conditions rather than a fixed property of
the deployment. The system described here demonstrates one concrete realization of that
premise: a three-state adaptive engine that reads both network quality metrics and
IDS-detected security events, and immediately propagates mode changes to every module
that touches encryption or delivery. Under High-Risk conditions, an adversary who has
triggered the escalation—whether through replay injection or authentication probing—
finds the surviving sessions simultaneously rotating Diffie--Hellman keys on every
message, hiding plaintext length behind uniform-size ciphertext, and interleaving
randomized delays into the retry schedule, all without requiring any operator
intervention.

Experimental evaluation confirms that state transitions occur at the specified
thresholds and that the thirty-second hysteresis window prevents premature downgrade
under borderline loss rates. Ratchet forward secrecy and break-in recovery are verified
empirically, and constant-payload-size enforcement is confirmed at the packet capture
level. All thirteen functional tests pass.

The most significant architectural limitation—that the server decrypts each message in
memory to perform routing and re-encryption, making it a trusted relay—remains open.
Addressing it requires adopting X3DH pre-key exchange~\cite{b6} so that the server
forwards encrypted blobs without ever seeing plaintext. Extending the broadcast
mechanism from per-client encryption loops to a proper group ratchet along the lines
of MLS~\cite{b5} is the second near-term priority. Both directions are well-defined
and build directly on the cryptographic infrastructure already in place.
