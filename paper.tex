\begin{abstract}
Secure messaging over unreliable and adversarial networks is undermined by static security
configurations that cannot respond to changing threat conditions. We present an adaptive
end-to-end encrypted chat system that combines TLS 1.3 transport security with a
Signal-protocol Double Ratchet at the application layer, dual-path TCP and UDP delivery,
and a three-state adaptive engine that automatically reconfigures cryptographic and
transport parameters in response to live network metrics and detected security events.
A lightweight per-IP intrusion detection system feeds authentication failures and replay
detections directly into the engine state machine, triggering escalation from Normal to
Unstable or High-Risk mode with immediate effect. In High-Risk mode, all payloads are
padded to a constant 4096 bytes, DH ratchet steps occur on every message, and randomized
retry delays frustrate traffic analysis. The system provides forward secrecy and
break-in recovery per the Double Ratchet specification, multipath deduplication via a
128-bit message-ID ring buffer, and persistent offline message delivery. Evaluation
confirms correct state transitions under injected packet loss and authentication failure
scenarios, with all 13 functional tests passing.
\end{abstract}

\section{Introduction}

Over the past decade, secure messaging has become a foundational requirement across
civilian, enterprise, and operational communication contexts alike. The cryptographic
primitives underlying these systems have matured considerably: Transport Layer Security
version~1.3~\cite{b3} provides authenticated encryption with forward secrecy at the
session level, and application-layer protocols such as the Signal Double
Ratchet~\cite{b1} extend those guarantees to the per-message level. What has received
comparatively less attention is the relationship between a system's operating environment
and its security posture. Most deployed systems apply a fixed cryptographic configuration
chosen at design time, then rely on that configuration to hold regardless of what the
network or the adversary actually does.

This assumption breaks in practice. A link experiencing 20\% packet loss calls for
different retry behavior than one that is healthy; a session under active authentication
brute-force warrants tighter key rotation and IP-level blocking that a session seeing
no failures does not. Static configurations cannot express this distinction. The result
is either a posture that is permanently tuned for the worst case—accepting unnecessary
overhead under benign conditions—or one tuned for the common case, leaving the system
underdefended when conditions deteriorate.

This paper describes a multi-client end-to-end encrypted chat system, implemented in
C~(C11, POSIX), that treats security posture as a runtime variable. The system combines
TLS~1.3 transport encryption with a Signal-style Double Ratchet at the application
layer, simultaneous dual-path delivery over TCP and UDP, and a three-state adaptive
engine whose inputs are drawn from both network quality measurements and a co-resident
per-IP intrusion detection system~(IDS). When the engine determines that conditions have
degraded—through rising packet loss, detected replay attempts, or a concentration of
authentication failures from a single address—it escalates its operating mode and
immediately reconfigures cryptographic and transport parameters across all active
sessions. Recovery to the baseline mode is intentionally hysteretic, requiring thirty
consecutive seconds of stable metrics before downgrading, to avoid oscillatory behavior
under borderline conditions.

The main contributions of this work are as follows:
\begin{enumerate}
    \item A three-state adaptive engine (Normal, Unstable, High-Risk) driven by a
          rolling packet loss rate, smoothed round-trip time, per-session authentication
          failure count, and cumulative replay detection count.
    \item Integration of the Signal Double Ratchet at the application layer, providing
          per-message forward secrecy and break-in recovery independently of the
          underlying TLS session state.
    \item Simultaneous dual-path delivery over TCP and UDP with deduplication via a
          128-bit message-ID ring buffer, ensuring message delivery resilience when
          either transport path experiences loss.
    \item A lightweight per-IP IDS that routes security events directly into the
          adaptive state machine, collapsing threat detection and cryptographic response
          into a single feedback loop.
    \item A persistent offline message queue with timestamp-ordered replay on client
          reconnection, decoupled from ratchet state to accommodate asynchronous delivery.
\end{enumerate}

The remainder of this paper is organized as follows. Section~II surveys related work.
Section~III describes the overall system architecture. Sections~IV and~V detail the
wire protocol and cryptographic design. Sections~VI and~VII cover the adaptive engine
with IDS coupling and the multipath transport with offline queuing. Section~VIII
presents evaluation results, Section~IX discusses limitations and future directions,
and Section~X concludes.

\section{Related Work}

\subsection{End-to-End Messaging Protocols}

The Signal Double Ratchet Algorithm~\cite{b1} has become the dominant construction for
asynchronous end-to-end encrypted messaging. Unlike earlier session-based schemes that
derived a single key for an entire conversation, the Double Ratchet chains two
interlocked key derivation functions: a symmetric ratchet that advances on every message,
and a Diffie--Hellman ratchet that periodically injects fresh entropy from a new
ephemeral key exchange. The combination means that an attacker who recovers the chain
state at any point in time cannot derive keys for messages outside the current DH epoch.
Cohn-Gordon et al.~\cite{b2} provided the first rigorous security proof of this
construction, establishing forward secrecy and post-compromise security as formally
provable properties. Our implementation follows the Double Ratchet specification
directly, adding DH ratchet frequency as an adaptive parameter so that the engine can
increase key turnover under adversarial conditions.

\subsection{Transport Layer Security}

TLS~1.3~\cite{b3}, standardized in RFC~8446, eliminated several weaknesses carried
forward from prior versions: static RSA key transport (which provides no forward
secrecy), negotiable cipher suites including known-weak constructions, and a
renegotiation mechanism that introduced side-channel risk. Version~1.3 mandates
ephemeral (EC)DHE key exchange in every handshake and restricts cipher suites to a
small set of authenticated encryption schemes. Our system configures OpenSSL to reject
any version below 1.3, ensuring that the session-level protection cannot be silently
downgraded. HKDF~\cite{b4}, specified in RFC~5869, underlies both the TLS~1.3 key
schedule and our application-layer ratchet initialization, providing a clean separation
between entropy extraction and key expansion.

\subsection{Adaptive and Context-Aware Security}

The principle of adjusting system behavior in response to measured environmental
conditions is well established in network management—adaptive bitrate streaming adjusts
video quality to link capacity, and congestion control algorithms continuously revise
transmission rate. Applying the same feedback principle to cryptographic policy has
received considerably less attention in the literature. Most deployed secure messaging
systems configure retry counts, padding behavior, and key rotation schedules as fixed
constants. Our adaptive engine treats these as outputs of a state machine whose inputs
are live network and security metrics, aligning the principle of least privilege with
current threat level rather than worst-case assumptions.

\subsection{Group Messaging Security}

The Messaging Layer Security protocol~\cite{b5}, standardized as RFC~9420, addresses
the scalability limitations of pairwise key establishment for group conversations through
a tree-structured key agreement scheme (TreeKEM) that achieves logarithmic message
complexity in the number of group members. Our current design handles broadcast as a
loop of directed per-client encryptions, which is functionally correct for small groups
but does not scale to larger deployments. Extending the system to MLS-style group
ratcheting is identified in Section~IX as the primary direction for future work.

\section{System Architecture}

The system follows a two-tier client-server architecture. The server listens on TCP
port~8080 (primary, TLS-wrapped) and UDP port~8081 (backup path). Clients connect over
both transports simultaneously after the TLS handshake completes on the TCP channel.

\subsection{Server}

The server is a single long-running POSIX process. An \texttt{accept()} loop blocks on
the TCP socket; each accepted connection is handed to a newly spawned detached
\texttt{pthread} executing \texttt{handle\_client()}, which manages the TLS handshake,
DH key exchange, authentication, message routing, and eventual cleanup for that client.
This thread-per-connection model isolates per-client state while supporting up to 50
concurrent sessions (\texttt{MAX\_CLIENTS}). All threads that read or write the client
registry share a single \texttt{pthread\_mutex\_t} that serializes access to the
\texttt{ClientEntry[50]} table.

Two background threads run independently of client connections. The adaptive engine
thread evaluates the rolling \texttt{Metrics} structure once per second and writes the
current operating mode to a shared \texttt{EngineState} variable; all other modules
read this variable without acquiring a lock, tolerating at most a one-tick lag. A
dedicated UDP receiver thread drains the UDP socket continuously, subjects each received
frame to the same 128-bit message-ID deduplication check used on the TCP path, and
forwards unique frames to the appropriate client handler.

When a client disconnects, the server removes the corresponding entry from the client
table and broadcasts an updated user list to all remaining sessions. Messages sent to a
recipient who is offline at delivery time are written to the persistent offline queue
and delivered—re-encrypted with the recipient's current ratchet state—upon reconnect.

\subsection{Client}

Two client implementations are provided: a GTK3 graphical client and a command-line
client. Both share the same underlying networking and cryptographic modules and differ
only in their presentation layers.

Each client runs two threads after authentication completes. The \emph{send thread}
dequeues outgoing messages from the three-level priority queue in priority order,
derives the next message key from the ratchet, encrypts the padded plaintext under
AES-256-CBC, and transmits the resulting frame over both the TLS/TCP and UDP paths.
The \emph{receive thread} reads from the TLS socket, checks the message ID against the
local deduplication ring buffer, decrypts the payload, and delivers it to the UI layer.
In the GTK client, delivery is posted to the GTK main loop via
\texttt{gdk\_threads\_add\_idle()} so that all widget mutations occur on the UI
thread. In the CLI client, the receive thread writes directly to standard output.

\section{Wire Protocol and Connection Lifecycle}

Every message uses a uniform 28-byte binary header:

\begin{equation}
\underbrace{\texttt{ver}(1)}_{}\ |\ \underbrace{\texttt{type}(1)}_{}\ |\ \underbrace{\texttt{pri}(1)}_{}\ |\ \underbrace{\texttt{flags}(1)}_{}\ |\ \underbrace{\texttt{msg\_id}(16)}_{}\ |\ \underbrace{\texttt{len}(4)}_{}\ |\ \underbrace{\texttt{crc32}(4)}_{}
\end{equation}

The 128-bit \texttt{msg\_id} is used for deduplication across TCP and UDP paths.
All \texttt{MSG\_CHAT} payloads are padded to a constant 4112 bytes
(16-byte IV + 4096-byte AES ciphertext) to resist traffic analysis.

%  SECTION V — CRYPTOGRAPHIC DESIGN  (Member 2)
% ============================================================
\section{Cryptographic Design}

\subsection{Cryptographic Stack}

The system employs a four-layer cryptographic stack:

\begin{enumerate}
    \item \textbf{Key Agreement} --- X25519 ECDH (\texttt{MSG\_DH\_INIT} /
          \texttt{MSG\_DH\_RESP}). The shared secret is expanded via HKDF~\cite{b4}
          to produce initial ratchet keys.
    \item \textbf{Identity Authentication} --- RSA-2048 signatures over the username
          bytes. The server stores the public key on first login and verifies it on
          subsequent logins.
    \item \textbf{Transport Confidentiality} --- TLS 1.3~\cite{b3} with TLS 1.2
          and below disabled.
    \item \textbf{E2EE Confidentiality} --- AES-256-CBC with per-message keys derived
          from the Double Ratchet chain. Operates inside TLS so that TLS compromise
          does not expose message content.
\end{enumerate}

\subsection{Double Ratchet Protocol}

The Double Ratchet~\cite{b1} maintains two interlocked ratchets. The symmetric ratchet
advances on every message:
\begin{align}
    \textit{msg\_key}       &= \text{HMAC-SHA256}(\textit{chain\_key},\ \texttt{0x01}) \\
    \textit{new\_chain\_key} &= \text{HMAC-SHA256}(\textit{chain\_key},\ \texttt{0x02})
\end{align}
Each message uses a unique derived key; the old chain key is discarded immediately.
The DH ratchet injects fresh Diffie--Hellman entropy every \texttt{dh\_ratchet\_freq}
messages, providing break-in recovery. In High-Risk mode this frequency is set to 1,
meaning a new X25519 keypair is generated per message.

All key material is erased with \texttt{OPENSSL\_cleanse()} immediately after use.

\section{Adaptive Engine and Intrusion Detection}

\subsection{Three-State Adaptive Engine}

A background thread evaluates a \texttt{Metrics} structure every second and updates the
shared engine state read by all modules. Three operating modes are defined:

\begin{itemize}
    \item \textbf{Normal} --- standard retries (3), 100\,ms retry delay, DH ratchet
          every 10 messages.
    \item \textbf{Unstable} --- increased retries (7), 200\,ms delay; triggered by
          $\geq$5\% packet loss or $\geq$3 consecutive timeouts.
    \item \textbf{High-Risk} --- maximum retries (10), 300\,ms base delay, forced
          4096-byte padding, random 100--500\,ms delays, DH ratchet every message;
          triggered immediately by $\geq$20\% packet loss, $\geq$5 auth failures, or
          $\geq$3 replay detections.
\end{itemize}

Escalation is immediate. Downgrade to Normal requires 30 seconds of stable metrics
(hysteresis to prevent state thrashing).

\subsection{Intrusion Detection System}

The IDS maintains a table of 256 per-IP records. After five authentication failures
from the same IP, the address is blocked for 300 seconds and
\texttt{metrics\_record\_auth\_fail()} is called, escalating the engine to High-Risk.
Replay detections likewise call \texttt{metrics\_record\_replay()}. Blocked IPs are
rejected before the TLS handshake completes.

%  SECTION VII — MULTIPATH TRANSPORT AND OFFLINE QUEUE  (Member 3)

\section{Multipath Transport and Offline Message Queue}

\subsection{Dual-Path Delivery}

Every outgoing message is transmitted over both the TLS/TCP primary path and a UDP
backup path simultaneously. A 1024-slot deduplication ring buffer keyed on the 128-bit
\texttt{msg\_id} discards duplicate deliveries silently. The ring buffer is
\texttt{O(1024)} at typical chat rates and protected by a \texttt{pthread\_mutex\_t}.

\subsection{Priority Queue}

The client send thread drains a three-level priority queue: Normal, Urgent, and
Critical. Critical messages wake the send thread immediately and receive two additional
multipath retry attempts.

\subsection{Offline Message Queue}

Messages addressed to a disconnected recipient are stored on disk under
\texttt{data/offline\_queue/<username>/} as one file per message, named by millisecond
timestamp and message ID for lexicographic chronological ordering. Plaintext is stored
(not ciphertext) because the recipient's future ratchet key is unknown at queue time;
re-encryption occurs when the recipient reconnects. Queue capacity is 500 messages per
user. Directories are mode \texttt{0700} and files \texttt{0600}; usernames are
validated against \texttt{[a-zA-Z0-9\_-]} to prevent directory traversal.

\section{Evaluation}

\subsection{Functional Correctness}

All 13 functional tests pass. Key results are summarised below:

\begin{itemize}
    \item \textbf{Ratchet key uniqueness}: 100 derived message keys are all distinct.
    \item \textbf{Forward secrecy}: deleting ratchet state at message 50 leaves all
          prior messages unrecoverable.
    \item \textbf{Break-in recovery}: exposing the chain key at message 50; messages
          after the subsequent DH ratchet step are unreadable to an attacker holding
          that chain key.
    \item \textbf{Constant payload size}: all \texttt{MSG\_CHAT} frames are 4112 bytes
          as confirmed via \texttt{tcpdump}.
    \item \textbf{Multipath dedup}: the same \texttt{msg\_id} arriving via TCP and UDP
          is processed exactly once.
    \item \textbf{Engine transitions}: injecting 6\% packet loss triggers
          Normal$\to$Unstable; 21\% triggers Unstable$\to$High-Risk; 5 auth failures
          trigger immediate escalation to High-Risk from any state.
    \item \textbf{Hysteresis}: 30 seconds of stable metrics after High-Risk produces
          a return to Normal.
    \item \textbf{IDS block}: 5 auth failures from one IP blocks it; TLS handshake
          refused. Block lifted after 300 seconds.
\end{itemize}

\section{Limitations and Future Work}

The current design has several acknowledged limitations. First, the server acts as a
trusted re-encryption relay: each \texttt{MSG\_CHAT} is decrypted with the sender's
ratchet and re-encrypted with the recipient's ratchet, so plaintext passes through
server memory. Pure end-to-end encryption in the Signal sense would require X3DH
pre-key exchange~\cite{b6} so the server never sees plaintext. Second, offline queued
messages are stored as plaintext, exposing them in the event of a server breach.
Third, TLS certificates are self-signed, suitable for lab evaluation but not
production deployment. Fourth, RSA keypairs are stored as plain files rather than
in hardware security modules. Fifth, broadcast messaging is implemented as a loop of
per-client directed encryptions rather than a proper group ratchet such as
MLS~\cite{b5}. Addressing these limitations, particularly adopting X3DH and MLS,
constitutes planned future work.

\section{Conclusion}

The central premise of this work is that cryptographic and transport configuration
should be a function of measured operating conditions rather than a fixed property of
the deployment. The system described here demonstrates one concrete realization of that
premise: a three-state adaptive engine that reads both network quality metrics and
IDS-detected security events, and immediately propagates mode changes to every module
that touches encryption or delivery. Under High-Risk conditions, an adversary who has
triggered the escalation—whether through replay injection or authentication probing—
finds the surviving sessions simultaneously rotating Diffie--Hellman keys on every
message, hiding plaintext length behind uniform-size ciphertext, and interleaving
randomized delays into the retry schedule, all without requiring any operator
intervention.

Experimental evaluation confirms that state transitions occur at the specified
thresholds and that the thirty-second hysteresis window prevents premature downgrade
under borderline loss rates. Ratchet forward secrecy and break-in recovery are verified
empirically, and constant-payload-size enforcement is confirmed at the packet capture
level. All thirteen functional tests pass.

The most significant architectural limitation—that the server decrypts each message in
memory to perform routing and re-encryption, making it a trusted relay—remains open.
Addressing it requires adopting X3DH pre-key exchange~\cite{b6} so that the server
forwards encrypted blobs without ever seeing plaintext. Extending the broadcast
mechanism from per-client encryption loops to a proper group ratchet along the lines
of MLS~\cite{b5} is the second near-term priority. Both directions are well-defined
and build directly on the cryptographic infrastructure already in place.
