\begin{abstract}
Deployed systems are not well equipped to deal with the dynamic security conditions at runtime for static security configuration. We introduce a multi-client end-to-end encrypted chat system using C11 on POSIX which makes security posture a runtime variable and not a compile-time constant. TLS~1.3 transport security is layered on top of Signal-protocol Double Ratchet at the application layer, and all messages are sent at once via both TCP and UDP. The three-state adaptive engine polls smoothed packet-loss rates, authentication errors per session, and replay-detected events once per second and immediately sends reconfigured cryptographic and transport parameters to all active sessions. All the message payloads are padded to the same length (4,096~bytes) and a new X25519 keypair is created per message in High-Risk mode, to resist traffic analysis and reduce the amount of exposure following post-compromise. A statically allocated intrusion-detection subsystem is based on a lightweight, real-time, per-IP authentication failures and replay events that are directly coupled to the engine's state machine, allowing threat detection and cryptographic responses to be performed within a single feedback loop. Deduplication is done on both delivery paths using a 128-bit message-ID ring buffer, and on-disk offline queue – messages to disconnected recipients are stored in the offline queue within an OS enforced access-control boundary. 13 functional tests are passed: Authentications are simulated by brute force, injected packet loss is simulated, and all tests are passed.
\end{abstract}

\section{Introduction}

In the last ten years, secure messaging has gone from a niche to a standard requirement in both civilian and operational settings. These systems have developed very good cryptographic primitives: TLS version 1.3 \cite{b3} offers session-level encryption that is authenticated and forward-secret at the transport layer; the Signal Double Ratchet algorithm \cite{b1} extends comparable guarantees to the individual message level. Much less discussed is the connection between an environment in which a system operates and the security stance of that system.

The majority of deployed secure messaging systems can be statically configured at design time and remain fixed over time as network conditions or hostile factors change. In practice, this is a significant restriction. When the link drops 20% of packets, it requires different behaviour to be applied to it when it is retried than when it is healthy; when a session is being brute-forced using active authentication, more frequent key rotations and IP-level blocking are warranted than for a quiet session. Such a distinction can only be made in a dynamic situation: either a posture is permanently configured for the worst case, thus wasting resources unless conditions are severe or a posture is optimized for the common case, leaving the system underdefended when conditions get worse.

A multi-client end-to-end encrypted chat system is described which implements security as a run-time parameter, realised in C11 on POSIX. It includes an adaptive engine that listens to network quality metrics and to IDS-identified security events to adjust encryption and transport parameters as needed, a three-state engine, a Signal-protocol Double Ratchet at the application layer, and TLS~ 1.3 transport security, as well as simultaneous dual-path message delivery over both TCP and UDP. A co-resident per-IP intrusion-detection subsystem (IDS) directly passes authentication failures and replay events to the engine's state machine. The main contributions of this work are:

\begin{enumerate}
    \item Three-state adaptive engine based on smoothed packet-loss rate, per-session authentication failure counter and a cumulative replay counter.
    \item Double Ratchet at the application level which includes per-message forward secrecy, and the ability to recover quickly if session-keys are compromised.
    \item Resilient delivery of messages over simultaneous dual-path delivery (TCP & UDP) with 128-bit message-ID deduplication.
    \item Lightweight, statically allocated IDS that takes per-IP security events directly into the adaptive state machine, combining threat detection and cryptographic response in one feedback loop.
\end{enumerate}

A persistent offline message queue with timestamp ordered filenames allows ordered replay on a client reconnection without tying queue state to an active ratchet state, thus allowing for fully asynchronous delivery.

The rest of this paper is structured as follows. The related research is surveyed in Section~II. The overall system architecture is described in Section~III. The wire protocol is described in detail in section~IV, and the design of the cryptographic system is described in section~V. Sections~VI and~VII describe the adaptive engine and IDS integration and multipath transport and offline queuing. The results of evaluations are reported in Section~VIII. Section~IX discusses limitations and future directions, and Section~X concludes.

\section{Related Work}

\subsection{End-to-End Messaging Protocols}

A variant of the Double Ratchet Algorithm has emerged as the common structure of an asynchronous end-to-end encrypted messaging system: the Signal \cite{b1} protocol. The Double Ratchet is a variant of the ratchet that takes two interlocked key-derivation functions: a symmetric ratchet to generate a new key on every message sent, and a Diffie--Hellman ratchet to periodically add new entropy from a new ephemeral key exchange. The result is that if an attacker is able to recover the chain state at any point in time, they can't produce any keys for messages outside the current DH epoch. The first formal security proof for this construction was given by Cohn-Gordon et al. \cite{b2} who proved forward secrecy and post-compromise security. Our implementation is a straight copy of the Double Ratchet specification, with DH ratchet frequency being adaptive, increasing automatically when the conditions are bad.

\subsection{Transport Layer Security 1.3}

RFC~8446 (TLS~1.3) \cite{b3} addressed several shortcomings of its predecessors: static RSA key transport (no forward secrecy), renegotiation and weak or susceptible to downgrade: attack cipher suites. Version~1.3 requires ephemeral (EC)DHE key exchange with all handshakes, and only allows a limited set of cipher suites that support authenticated encryption schemes. By default, our system will not allow anything less than TLS~1.3, which means that there is no possibility of downgrade of session-level protection. Our application-layer ratchet initialization is based on HKDF \cite{b4} (RFC5869), which is also used in the TLS~1.3 key schedule, providing separation of the entropy extraction and key expansion.

\subsection{Adaptive and Context-Aware Security}

For example, adaptive bitrate streaming—variations in video quality based on available bandwidth—is a standard practice in network management, and congestion control algorithms continuously adjust the rate on which packets are sent, based on the packet loss observed. A similar feedback principle is not much discussed in the literature in the context of cryptographic policy. The majority of implemented secure messaging systems have fixed key rotation periods, padding policies, and retries. The adaptive engine uses these parameters as outputs of a state machine, where the inputs are actual network and security metrics, so as to provide protection at an appropriate level relative to the threat level measured during runtime instead of worst-case scenarios.

\subsection{Group Messaging Security}

The Messaging Layer Security protocol \cite{b5} also tackles the scalability problem of pairwise encryption for group conversations by proposing a group key agreement scheme (TreeKEM) with a logarithmic number of messages in the number of group members, which is standardized as RFC~9420. The current design is based on a per-client directed encryption loop, suitable for small groups, but not for large deployments. One of the main directions suggested for future work in Section~IX is the extension of the system to MLS-style ratchet trees.

\section{System Architecture}

The system is a two-tiered client-server system. A backup transport path is set up, with a TLS-wrapped TCP socket on port~8080, and a plain UDP socket on port~8081, both of which are bound on the server. The application-layer DH key exchange starts after a TLS handshake on the TCP channel has been completed by the client and the server.

\subsection{Server}

The server is implemented as one long running process in the POSIX model. The \texttt{accept()} loop hangs on the TCP socket; each new connection accepted is detached to a new \texttt{pthread} which performs the TLS handshake, DH key exchange, authentication, message routing, and eventual teardown of that client. Each connection represents a single state, this thread per connection approach provides strict per-client state. There is a limit of \texttt{MAX\_CLIENTS}~=~50 concurrent sessions, and all threads that access the shared client registry will do so in series, through one mutex on \texttt{ClientEntry[50]}.

There are two background threads that run independent from Client connections. Once per second, an adaptive engine thread examines the current metrics structure, and stores the resulting operating mode in a shared variable, EngineState, which is read by all other modules without any locking, with a maximum of 1 tick of latency. A separate thread is used for receiving frames on a UDP socket, and sends each frame through exactly the same 128-bit message-ID deduplication check that occurs on the TCP path before the unique frames are passed to the client handler.

The server will process an incoming chat message, find the destination entry in the client table, and send it to all the active sessions, and broadcast an update of the user list. If the intended recipient is not online when the message is delivered, it is placed in a persistent, on-disk offline queue and is re-delivered, with the message being re-delivered again and re-encrypted by the recipient's current ratchet state when it is reconnected.

\subsection{Client}

Once the authentication is done, every client will execute two threads. The send thread removes messages from a three-level priority queue in priority order, generates the next message key based on the current ratchet, encrypts the padded plaintext using that key and sends the frame simultaneously using TLS/TCP and UDP. The receive thread consumes the message from the TLS socket, verifies the message ID against the local deduplication ring buffer, decrypts the payload and passes it to the UI layer. In the GTK client, the delivery is placed on the main loop using \texttt{gdk\_threads\_add\_idle()}, ensuring that all the mutations of widgets are done on the UI thread; in the CLI client, the receive thread directly writes to the standard output.

\section{Wire Protocol and Connection Lifecycle}

\subsection{Packet Framing and Header Structure}

Every message carries a common 28-byte binary header that includes a 128-bit \texttt{msg\_id} field used for deduplication across both the TCP and UDP delivery paths. All \texttt{MSG\_CHAT} payloads in High-Risk mode are padded so that the total encrypted frame is a fixed 4,112~bytes: a 16-byte IV (4-byte nonce prefix concatenated with a 12-byte nonce) followed by 4,096~bytes of AES ciphertext. This uniform frame size defeats traffic-analysis attacks that infer message content or length from observed packet sizes.

\section{Cryptographic Design}

The security architecture employs several cryptographic mechanisms in series so that each layer provides independent defense. Rather than relying on any single protection mechanism, the design integrates transport-level security, public-key identity verification, ephemeral session-key establishment, continuous key evolution through the Double Ratchet, and message-level symmetric encryption into a cohesive layered architecture. The complete structure of this layered design is illustrated in Fig.~\ref{fig:cryptoarch}.

\begin{figure}[htbp]
\centering
\includegraphics[width=\columnwidth]{4.png}

Six successive layers---TLS\,1.3 transport security, RSA-2048 authentication, X25519 DH key exchange with HKDF, Double Ratchet message-key evolution, AES-256-CBC message encryption, and key and memory hygiene---collaborate to provide secure channel establishment, identity assurance, forward secrecy, break-in recovery, constant-size padded ciphertext, and secure key management respectively.}
\label{fig:cryptoarch}
\end{figure}

The system employs four interlocked cryptographic layers:

\begin{enumerate}
    \item \textbf{Session Key Agreement} --- X25519 ECDH (\texttt{MSG\_DH\_INIT} / \texttt{MSG\_DH\_RESP}) establishes a shared secret, which HKDF \cite{b4} then expands into the initial ratchet root and chain keys.
    \item \textbf{Identity Authentication} --- RSA-2048 signatures over the username bytes authenticate both parties; the public key is registered on the server at first login and verified on every subsequent authentication.
    \item \textbf{Transport Confidentiality} --- TLS~1.3 wraps all TCP I/O; OpenSSL is configured to reject TLS~1.2 and earlier, preventing silent protocol downgrade.
    \item \textbf{Message-Level Confidentiality} --- AES-256-CBC with per-message keys derived from the Double Ratchet chain provides end-to-end encryption that operates inside the TLS tunnel and does not expose message content even if the TLS session were compromised.
\end{enumerate}

\subsection{Double Ratchet Key Evolution}

The Double Ratchet \cite{b1} advances its symmetric ratchet on every message:
\begin{align}
    \text{msg key} &= \text{HMAC-SHA256}(\text{chain key},\ \texttt{0x01}) \\
    \text{new chain key} &= \text{HMAC-SHA256}(\text{chain key},\ \texttt{0x02})
\end{align}
Each message thus uses a distinct derived key, and the old chain key is discarded immediately after the derivation step. The DH ratchet injects additional Diffie--Hellman entropy every \texttt{dh\_ratchet\_freq} messages, providing break-in recovery. In High-Risk mode this frequency is set to~1, causing a new X25519 keypair to be generated for every message and maximizing the rate of key material turnover. All ephemeral key material is erased with \texttt{OPENSSL\_cleanse()} immediately after use.

\section{Adaptive Engine and Intrusion Detection}
\label{sec:adaptive_engine}

\subsection{Three-State Adaptive Engine}

The adaptive engine translates measured operating conditions into concrete cryptographic and transport parameter changes. Rather than applying a single design-time configuration, the engine continuously monitors a set of network and security indicators and rewrites the active parameter set whenever thresholds are crossed. A background daemon thread performs one evaluation cycle per second, collecting telemetry from all active client sessions and collapsing it into a shared \texttt{Metrics} structure.

The following metrics are tracked and refreshed on each evaluation cycle:
\begin{itemize}
    \item \texttt{packet\_loss\_rate}: a weighted rolling average computed over the most recent 100 packets sent.
    \item \texttt{rtt\_ms}: smoothed round-trip time maintained using an exponentially weighted moving average (EWMA).
    \item \texttt{auth\_fail\_count}: cumulative count of authentication failures observed from the current IP, used to detect brute-force activity.
    \item \texttt{replay\_count}: total number of duplicate message IDs detected during the current evaluation window.
    \item \texttt{consecutive\_timeouts}: number of consecutive socket-level timeout events observed for the active sessions.
\end{itemize}

At the end of each one-second sampling interval, the engine compares the collected metrics against pre-determined thresholds and selects the appropriate operating state. The system defines three states: Normal, Unstable, and High-Risk.

\subsubsection{State Transition Logic}
The engine transitions between execution modes according to the following rules.

\paragraph{a) High-Risk Escalation}
The engine escalates immediately to High-Risk mode when any one of the following conditions is met:
\begin{itemize}
    \item Rolling packet loss rate (RPLR) is at or above 20\%.
    \item Cumulative authentication failure count (\texttt{auth\_fail\_count}) reaches 5 or more.
    \item Cumulative replay count (\texttt{replay\_count}) reaches 3 or more.
\end{itemize}

\paragraph{b) Unstable Transition}
The engine transitions from Normal to Unstable when conditions degrade without reaching the High-Risk threshold:
\begin{itemize}
    \item Rolling packet loss rate exceeds 5\%.
    \item Consecutive socket-level timeouts reach 3 or more.
\end{itemize}

\paragraph{c) Normal Recovery and Hysteresis}
To prevent rapid oscillation across state boundaries, the engine applies a hysteresis mechanism: a downgrade to Normal occurs only after all monitored metrics have remained consistently below their respective Unstable thresholds for a continuous 30-second window.

On every state change, the server broadcasts a control frame to all connected clients and updates the global \texttt{EngineState} variable. The parameter changes associated with each state are listed in Table~\ref{tab:aprm}. Under degraded network conditions, the combination of smaller crypto chunk sizes and increased retry budgets yields substantially higher delivery rates on lossy links compared to the Normal-mode configuration.

In High-Risk mode, three additional defenses are activated simultaneously:
\begin{itemize}
    \item \textbf{Forced Padding}: All message payloads are padded to a uniform 4,096~bytes, preventing an observer from inferring message length from packet size.
    \item \textbf{Randomized Retry Delay}: Retransmissions are delayed by a random interval of 100--500\,ms, making timing-based traffic analysis substantially harder.
    \item \textbf{Aggressive DH Ratcheting}: The DH ratchet executes on every message (\texttt{dh\_ratchet\_freq}~=~1), maximizing forward secrecy and post-compromise recovery speed.
\end{itemize}

\subsection{Intrusion Detection System}

The server incorporates a lightweight, stateful intrusion-detection subsystem (IDS) designed to counter authentication brute-forcing and packet replay attacks. To avoid the overhead of dynamic allocation, the IDS uses a statically allocated tracking table bounded at \texttt{MAX\_BLOCKED\_IPS} entries, with operations optimized for constant-time per-packet lookup.

Each record in the tracking table stores the following fields:
\begin{itemize}
    \item Client IP address (stored as a string, up to 48 characters).
    \item A counter recording the number of authentication failures from that address.
    \item A boolean flag indicating whether the IP is currently blocked.
    \item A timestamp recording when the block was applied.
\end{itemize}

The IDS exposes two reporting interfaces: \texttt{ids\_record\_auth\_fail()} and \texttt{ids\_record\_replay()}. When an authentication attempt fails---for example, if an invalid RSA signature is received, or a client requests a username already bound to an active session---the IDS increments the failure counter for that IP. When the counter reaches~5, the following sequence executes automatically:
\begin{enumerate}
    \item The IP address is added to the blocked list.
    \item The current epoch time is recorded as the block timestamp.
    \item \texttt{metrics\_record\_auth\_fail()} is called, triggering immediate escalation of the adaptive state machine to High-Risk mode.
\end{enumerate}

Replay attacks are handled analogously: if an incoming message ID is already present in the deduplication ring buffer, the event is classified as a replay attempt and \texttt{metrics\_record\_replay()} switches the engine to High-Risk mode. Blocked IPs are enforced inside the server's \texttt{accept()} loop---connections from blocked addresses are dropped before the TLS~1.3 handshake begins, conserving CPU cycles. Block expiry is handled lazily to avoid a dedicated timer thread: \texttt{ids\_expire\_blocks()} is called within the main server loop after each received message, and if the elapsed time since an IP's block timestamp exceeds 300~seconds (5~minutes), the block flag is cleared and the tracking record is reset.

All blocking and unblocking actions are written to a dedicated IDS log file in the following format:
\begin{verbatim}
[IDS 2026-06-10 14:23:01] BLOCK from 192.168.1.50
[IDS 2026-06-10 14:28:01] UNBLOCK 192.168.1.50
\end{verbatim}

\section{Multipath Transport and Offline Queue}
\label{sec:multipath_transport}

\subsection{Dual-Path Delivery and Deduplication}

To improve transmission reliability under unstable or adversarial network conditions, the system adopts a simultaneous dual-path delivery approach: every outgoing message is sent over a primary TLS~1.3-encrypted TCP socket and a redundant UDP datagram path in parallel. The client send loop respects the retry budget configured by the adaptive engine, encrypting each frame and transmitting it on the TLS socket while simultaneously dispatching the same ciphertext as a UDP datagram. In High-Risk mode, the engine interposes a random delay of 100--500\,ms between retransmission attempts to obstruct timing-based traffic analysis; Normal and Unstable modes maintain a fixed retry interval. Messages assigned Critical priority receive two additional retry attempts beyond the baseline limit to maximize delivery probability.

Since both paths can deliver the same frame, the receiver must suppress duplicates. The receiving pipeline implements a thread-safe deduplication mechanism based on a circular buffer defined as:
\begin{verbatim}
dedup_buf[1024][16]
\end{verbatim}
This ring buffer holds up to 1,024 128-bit message IDs. On each incoming frame, the receiver calls \texttt{dedup\_check()}: if the message ID is already in the active window, the frame is silently dropped; otherwise \texttt{dedup\_add()} appends the ID (advancing the ring buffer pointer modulo 1,024) and forwards the payload for decryption. All deduplication operations are serialized through a \texttt{pthread\_mutex\_t}, and both lookup and insert run in constant time to avoid becoming a throughput bottleneck.

\subsection{Client-Side Priority Queue}

The client transmission pipeline incorporates a three-level priority scheduling mechanism for outgoing messages. Messages are classified into one of three priority levels:
\begin{itemize}
    \item \textbf{Normal (Priority~0)}: Processed in standard FIFO order.
    \item \textbf{Urgent (Priority~1)}: Queued ahead of Normal traffic to reduce propagation delay.
    \item \textbf{Critical (Priority~2)}: Assigned the highest scheduling priority and placed at the head of the queue.
\end{itemize}
When a Critical message is enqueued, the client calls \texttt{pthread\_cond\_signal()} to wake the send thread immediately if it is idle or blocked. Critical messages also receive extra retry attempts in the multipath delivery loop. Priority designations are carried across the network via the \texttt{MsgHeader.priority} field.

\subsection{Persistent Offline Message Queue}

When a message is addressed to a recipient who is not currently connected, the server provides asynchronous delivery through a persistent on-disk offline queue. The server's client handler serializes undeliverable messages to the recipient's queue directory at:
\begin{verbatim}
data/offline_queue/<username>/
\end{verbatim}
Before any filesystem access, the server validates the username against a strict regular expression (\texttt{[a-zA-Z0-9\_-]}) to prevent directory traversal attacks through embedded path separators such as \texttt{/../}. Directories are created with mode 0700 and message files with mode 0600, enforcing OS-level access control. Individual messages are saved as files named \texttt{<timestamp\_ms>\_<msg\_id\_hex>}; the timestamp-based naming allows the server to read the queue in lexicographical order on reconnection, preserving chronological message ordering.

A deliberate design decision was made to store offline messages as plaintext rather than ciphertext on the server. Because the recipient's ratchet state at queuing time is unknown until the moment of reconnection, pre-encrypting with the current ratchet state would cause synchronization problems and render the queued messages undecryptable on reconnect. Messages are instead protected at rest by OS-level access control permissions, and re-encrypted under the recipient's live ratchet state at the time of delivery. When replayed, these frames carry the \texttt{MSG\_FLAG\_IS\_OFFLINE\_REPLAY} flag, allowing the client UI to display a \texttt{[queued]} indicator and distinguish replayed traffic from live traffic. The offline queue is capped at \texttt{OFFLINE\_QUEUE\_MAX}~=~500 messages per user; messages arriving after this limit is reached are discarded.

\section{Evaluation}
\label{sec:evaluation}

This section details the empirical evaluation of the proposed system, focusing on cryptographic correctness, multi-path transport resilience, and the responsiveness of the adaptive security engine.

\subsection{Experimental Setup}

Experiments were conducted in a containerized environment replicating multiple real clients and a server. Network degradation was injected on the client-server loopback interface using the Linux Traffic Control (\texttt{tc}) utility combined with the \texttt{netem} network emulation module. Security-related events were triggered by script-driven authentication brute-force and packet replay injectors.

\subsection{Cryptographic and Functional Verification}

The cryptographic properties described in Section~V were tested empirically under standard operating conditions:
\begin{itemize}
    \item \textbf{Key Uniqueness \& Integrity:} All derived symmetric keys were verified as unique across 100 sequentially generated message keys. A round-trip test using AES-256-CBC successfully recovered the exact plaintexts in every case.
    \item \textbf{Forward Secrecy:} The client-side active ratchet state was deleted at message~50. Subsequent attempts to decrypt historical messages (1--49) failed in all cases, confirming that compromised state does not expose past traffic.
    \item \textbf{Post-Compromise Security (Break-in Recovery):} To simulate key compromise, the symmetric chain key was exposed at message~50. Following the next DH ratchet exchange---every 10 messages in Normal mode and every message in High-Risk mode---the attacker was unable to decrypt subsequent messages, verifying break-in recovery.
    \item \textbf{Traffic Analysis Mitigation:} Packet captures via \texttt{tcpdump} in High-Risk mode confirmed that the \texttt{MSG\_CHAT} payload was consistently 4,112~bytes (16-byte IV + 4,096-byte ciphertext) regardless of actual message content.
\end{itemize}

\subsection{IDS Metrics and Adaptive Engine}

The adaptive engine's transitions and operational parameters were verified across the following conditions:
\begin{itemize}
    \item \textbf{Packet Loss ($\ge$ 5\%):} Prompts a transition from Normal to Unstable mode. (Status: Pass)
    \item \textbf{Packet Loss ($\ge$ 20\%):} Prompts a transition from Unstable to High-Risk mode. (Status: Pass)
    \item \textbf{Authentication Failures ($\ge$ 5 from the same IP):} Triggers an immediate transition from any state to High-Risk mode. (Status: Pass)
    \item \textbf{Replay Attacks ($\ge$ 3 detections):} Triggers an immediate transition from any state to High-Risk mode. (Status: Pass)
    \item \textbf{Metrics Stability ($\ge$ 30 seconds below Unstable thresholds):} Triggers a downgrade to Normal mode. (Status: Pass)
\end{itemize}

\subsection{Other System Behaviors}

\begin{itemize}
    \item \textbf{Multi-Path Deduplication:} Under packet loss injection, identical messages were received on both the TLS/TCP and UDP paths. The 1,024-entry ring buffer correctly identified and suppressed all duplicates, delivering each unique message to the application layer exactly once.
    \item \textbf{Intrusion Blocking:} Exceeding five authentication failures from a single IP caused the IDS to blackhole that host. All subsequent connection attempts were dropped before the TLS handshake, conserving CPU cycles as expected.
    \item \textbf{Offline Replay:} Messages sent to disconnected users were queued on disk in chronological order. Upon client reconnection, the server re-encrypted and delivered the queued frames with the \texttt{MSG\_FLAG\_IS\_OFFLINE\_REPLAY} flag set, and the client reconstructed the chat history in the correct sequence.
\end{itemize}

\section{Limitations and Future Work}

While the proposed system presents a comprehensive layered security architecture, several limitations in the current design warrant clear discussion and systematic future attention.

\subsection{Trusted Server Relay and the Limits of End-to-End Encryption}

The most significant architectural limitation is the system's reliance on a trusted server relay for message forwarding. As described in Section~IV, the server fully decrypts each incoming message using the sender's Double Ratchet receive context in order to extract the intended recipient identifier from the plaintext payload, then re-encrypts the recovered plaintext under the recipient's send-ratchet context before forwarding. This server-visible decryption step is architecturally required by the current recipient-resolution design, and it means the system does not achieve strict end-to-end encryption semantics in the academic sense: the server briefly handles message plaintext. This is a deliberate design compromise that substantially simplifies offline message queuing, adaptive priority routing, and server-side session management, but it represents a clear departure from the security model offered by fully end-to-end encrypted systems such as Signal, where the server handles only opaque ciphertexts. An adversary who compromises the server infrastructure would have brief access to message plaintexts during the forwarding window. Future work should evaluate a pre-key distribution architecture in which recipients post signed pre-keys to the server in advance, allowing senders to encrypt directly to the recipient's pre-key without any server-side decryption. The X3DH key agreement protocol \cite{b6} and Signal's sealed-sender mechanism are well-defined reference designs for this capability.

\subsection{Offline Message Storage Security}

The offline message queue currently stores messages as plaintext on the server's persistent storage. While OS-level access control permissions and a per-user retention cap reduce exposure risk, the absence of at-rest encryption means that a successful compromise of the server's storage infrastructure---through access control failure, physical media theft, or backup interception---could expose all queued messages. Future designs should encrypt offline queued messages using recipient-derived keying material so that only the recipient, upon reconnecting, holds the key needed to decrypt the queued content. Combining this approach with X3DH pre-key distribution would eliminate any server-side plaintext exposure on the offline delivery path.

\subsection{Identity Management and Public-Key Infrastructure}

The current identity framework is well-suited to small, controlled deployments where membership is known and trust can be administered centrally. Each user self-asserts an RSA public key at registration with no certificate authority, revocation mechanism, or web-of-trust infrastructure. For large-scale or open-membership deployments this model has notable limitations: without a PKI there is no assurance that a presented public key belongs to the claimed identity, leaving the system vulnerable to long-term adversarial impersonation. The absence of key revocation further means that a compromised identity key cannot be invalidated without out-of-band coordination. Future work should evaluate certificate-based trust models, decentralized key-transparency logs, and key-management infrastructures sufficient for broader interoperability and revocation requirements.

\subsection{Scalability and Group Communication}

The current architecture supports only pairwise directed messaging: the server iterates over group members individually, causing both processing overhead and bandwidth to scale linearly with group size. Explicit group key management protocols with sublinear complexity---such as the MLS protocol \cite{b5} (RFC~9420), whose tree-based key structures reduce per-message overhead to O(log~$n$)---should be evaluated as extensions to the existing architecture.

\subsection{Adaptive Security Mechanisms and Threat Intelligence}

The current adaptive engine responds to simple heuristic signals such as packet loss rates and authentication anomaly counts. It does not incorporate richer contextual intelligence available in modern deployments. Future work should investigate behavioral analytics, peer-reputation scoring, and machine-learning-augmented threat classification to enable more precise security adaptation while reducing false escalations that impose unnecessary cryptographic overhead on legitimate users.

\subsection{Formal Verification}

Security analysis in this work is conducted at the design and architecture level; the protocol has not been verified against formal security properties using symbolic model checkers such as ProVerif or Tamarin, nor against computational proof frameworks. Formal verification is considered best practice for cryptographic protocols and is increasingly required by standards bodies for high-assurance deployments. Future work should formally model and mechanize the key security properties guaranteed by the protocol, including forward secrecy, break-in recovery, and authentication soundness.

\section{Conclusion}

The central premise of this work is that cryptographic and transport configuration should be a function of measured operating conditions rather than a fixed property of the deployment. The system described here demonstrates one concrete realization of that premise: a three-state adaptive engine that reads both network quality metrics and IDS-detected security events, and immediately propagates mode changes to every module that touches encryption or delivery. Under High-Risk conditions, an adversary who has triggered the escalation---whether through replay injection or authentication probing---finds the surviving sessions simultaneously rotating Diffie--Hellman keys on every message, hiding plaintext length behind uniform-size ciphertext, and interleaving randomized delays into the retry schedule, all without requiring any operator intervention.

Experimental evaluation confirms that state transitions occur at the specified thresholds and that the thirty-second hysteresis window prevents premature downgrade under borderline loss rates. Ratchet forward secrecy and break-in recovery are verified empirically, and constant-payload-size enforcement is confirmed at the packet capture level. All thirteen functional tests pass.

The most significant architectural limitation---that the server decrypts each message in memory to perform routing and re-encryption, making it a trusted relay---remains open. Addressing it requires adopting X3DH pre-key exchange~\cite{b6} so that the server forwards encrypted blobs without ever seeing plaintext. Extending the broadcast mechanism from per-client encryption loops to a proper group ratchet along the lines of MLS~\cite{b5} is the second near-term priority. Both directions are well-defined and build directly on the cryptographic infrastructure already in place.
